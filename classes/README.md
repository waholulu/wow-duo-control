# 共享刷怪流程与职业归档

## 划分原则

职业归档只隔离战斗差异。换职业继续使用已有的巡游、拾取、恢复、背包、导航和运行保护，不重新实现一套挂机系统，也不因切换职业而默认关闭这些功能。

| 层次 | 内容 | 当前入口 |
|---|---|---|
| 共享任务流程 | 检查背包 → 搜索 → 战斗 → 确认击杀 → 拾取确认 → 继续；无合适目标则巡游后重搜 | `runtime_main.Controller.patrol` |
| 共享技能 | 巡游、恢复、拾取、背包、导航、撤退；技能自己的完成/失败证据 | `runtime_skills.py`、`runtime_interactions.py` |
| 战斗差异 | 战前准备、技能绑定、接近方式、近战/施法节奏、资源阈值；未来按实测扩展治疗等 | `classes/<职业>/combat.json` → `class_profiles.policy_options` → `control_policy.Policy` |
| 人物与环境标定 | 血条位置、背包布局、光标、目标名称、地图/UI模板 | 当前由职业配置的 `vision_profile` 指向，允许 `--profile` 覆盖；这是当前人物/UI数据，不是职业固有能力 |
| 共享运行基础 | OBS取帧、KMBox独占、输入时效、调度、取消、时限、证据、复盘 | `runtime_engine.py`、`runtime_store.py` 等 |

共享算法按参数和已验证能力选择行为，不在巡游/拾取里写 `if 职业 == 圣骑士` 之类分支。例如点击移动是可复用的接近方式，圣骑士配置选择F8交互；其停止清理仍由共享执行器负责。资源恢复逻辑可共用，阈值可按职业不同。

现有共享模块无需为归档而搬家或复制；先复用，出现真实重复再抽取。修复通用问题应同时惠及术士、圣骑士和后续职业。人物/UI变化需要重标定，不等于共享功能被丢弃；历史实机验收不能自动证明新人物已通过。

## 当前职业差异

| 职业 | 战斗配置 | 当前战斗行为 |
|---|---|---|
| 术士 warlock | `warlock/combat.json` | 2键攻击、最短2.6秒间隔，新增6秒有界效果检查；施法条未标定明确未知 |
| 圣骑士 paladin | `paladin/combat.json` | 2圣印按24秒计时维护，接近后4审判，F8交互接近/普攻，满足条件时按冷却补审判；1备用 |

圣骑士点击移动开启，辅助“开启交互按键”关闭，避免优先交互尸体。短步近战接近的早期试验保留在历史记录中，当前默认采用F8。恢复阶段已通过F1选自己、3键圣光术的有限实机验证；战中补圣印采用输入确认后的计时维护，战中治疗与自动复活未实现。

共享行为现拆为 `resource_readiness.py`（资源等待）、`timed_effects.py`（必需增益计时）、`melee_rotation.py`（接近、起手、普攻与冷却技能）。它们作为 Policy 的行为组件复用同一份状态，保留深拷贝回滚和原接口；按能力参数启用，不按职业名分支。`control_policy.py` 继续负责目标连续性与决策顺序，恢复和交互沿用已有共享实现，不为拆分而复制。

本次审核另增加`cast_cycle.py`与`offensive_effects.py`，区分按键回执与施法效果；资源等待不暂停战斗/伤害超时。`run_permission.py`组合旧死亡复盘与当前暂停/输入效果证据，普通拉怪与关联目标防御分别处理审判冷却。全部按能力配置复用，不添加职业名行为分支。具体规则与未实测范围见 [审核修复](../COMBAT_AUDIT_FIXES_20260929.md)。

`threat_settlement.py` 统一战后与异常退出的安静判据：至少3个独立新鲜帧、连续3秒无威胁；战后总等待预算独立为8秒，持续受伤仍立即失败，不能以XP证明所有敌人消失。该修复仅离线验证，未证明已解决多怪选择或地形脱险。

剩余流程收敛也已落地：`runtime_safety.py`统一异常处理，`prepare`统一拉怪前恢复/增益检查，恢复法力取自policy配置；`workflow_state.py`提供按物品操作失效的短期背包缓存和有时效/画面变化保护的尸体位置提示。拾取前只等待生命恢复，下一次开战前检查法力。完整行为与未实测限制见 [流程收敛](../WORKFLOW_CONVERGENCE.md)。

技能执行参数以 `policy` 为唯一来源；`seal_maintenance`、`judgement` 仅保存实测说明与参数位置。审判实测冷却10秒、执行间隔10.2秒是有意保留的余量。`workflow` 是共享流程的配置接口，不是职业实现；当前不同值来自历史验证范围，暂不把圣骑士效率参数强加给术士。人物标定与持久门禁仍沿用现有路径；多人物身份迁移需另行设计兼容读取，禁止通过新路径绕过旧死亡门禁。

`--class` 只选择职业配置和默认人物标定；不改变共享任务的组成。主战斗与受攻击后的防御使用同一职业参数。默认职业仍为术士，圣骑士需显式选 `--class paladin`。

## 日常使用与单项测试

- 连续刷怪：`--task patrol`，默认包含巡游和拾取；无怪走两小步再重搜。
- 单项战斗验证：`--task combat`，结束后不会自动巡游/拾取，不能用它代表完整挂机流程。
- `--no-loot` 是用户明确选择的任务开关，与职业无关。
- 启用拾取时，所有职业均须确认拾取完成；未找到可确认尸体或未得到新拾取证据，返回 `loot_unconfirmed`，停止进入下一轮。显式取消保留取消结果。
- 商人、采矿、剥皮等原有模块仍在，按已有任务参数和验证状态使用，不因新增职业自动启用。

每次运行保存职业与视觉配置以及动作/结果。`bindings_verified`、`vision_verified` 表示相应标定允许试验，不代替正式验收。

## 新增职业时的检查

1. 复用共享patrol流程和已有技能；确认没有因单项测试而漏接模块。
2. 只补充该职业战前、接近和输出差异，以及当前人物的绑定/UI标定。
3. 回归共享顺序：无目标→巡游→重搜；击杀→拾取确认；未确认→停止。
4. 做当前人物实机验证，将新增差异和新证据归入其记录，不重置其他职业的历史。
