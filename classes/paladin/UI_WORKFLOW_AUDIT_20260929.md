# 界面与操作流程第二次审核

2026-09-29。游戏保持用户要求的暂停，计数15/20，死亡审查门禁不变。本轮只读已有代码/运行证据及公开资料，并离线修改、回放CV计算；没有连接游戏、改变界面、复活或试打。

## 结论与耗时证据

最先做的应是同时显示战斗与拾取消息，随后减少无物品变化时的开包检查、缩短尸体搜索路径。继续压缩安全观察或提高鼠标步长，收益和可靠性都不如前两项。

以下是31轮events.jsonl的任务时长，包含各任务内部的等待和识别，并非纯技能施法时间：

| 项目 | 实测 | 含义 |
|---|---:|---|
| 3次成功战斗 | 14.63 / 10.29 / 22.13秒 | 输出并非当前最大瓶颈 |
| 2次拾取 | 51.63 / 70.52秒 | 共122.15秒 |
| 拾取鼠标移动指令 | 25 / 41次 | 切页、返回场景、定位尸体反复往返 |
| 已确认拾取并发出停止移动后，至拾取任务结束 | 20.92 / 21.57秒 | 主要是返回战斗记录页及确认；不是还在收物品 |
| 背包检查 | 7次，共39.05秒 | 包含未开战成功、没有拾取的重搜循环 |

证据：`runs/ui-workflow-second-audit-timing.json`，由29、31轮事件时间戳计算。两轮状态、空间、目标不同，不能直接将耗时差归因于某一次代码修改，也不能承诺消除切页后恰好节省同样秒数。

## 1. 原生界面可改进的地方

### P0：战斗记录与拾取消息分别常驻

建议把战斗记录移为独立窗口，另设一个小窗口仅显示自己的物品/金币拾取消息，两块不遮挡玩家条、目标框、技能距离提示或尸体搜索区域。固定位置、尺寸和字体，完成标定后锁定。

这样可以删除每次拾取前后的两次切页，以及移开鼠标确认标签的步骤；拾取期间仍可观察受击记录。公开的原生UI源码包含窗口脱离停靠、字体和背景不透明度设置，但不能证明当前客户端菜单完全相同，后续先现场核实。来源：[原生浮动聊天窗口源码镜像](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_ChatFrameBase/Mainline/FloatingChatFrame.lua)。不调用其中的游戏API，只通过原生设置和采集画面实施。

当前代码尚不能只靠拖动窗口就工作：`coin_receipt.py` 与 `LootVision.loot_messages()` 坐标写死，`CombatLogReader` 用“战斗标签被选中”判断可用。实施时必须把两块文字ROI配置化，改为各自的可见锚点，并校准遮挡/布局失效检测。不能简单删除 select_chat() 而继续读取旧坐标。

### P0：一个固定筛选同时保留输出、受击和死亡

当前最后选择的是“我发生了什么”子筛选，主标签识别不能证明输出日志可见。下一次界面调整应核实能否建立“与自己有关”的筛选：本人造成伤害、本人受到伤害、自己和相关目标死亡；去掉无关玩家、频道、增益刷屏等消息。固定一种详细程度，宽度以实际攻击/受击句子不折行为准，再选择可辨认的字号和较深背景。

必须保留怪名和“你”的主客体关系，不把全部文字简化为数值，也不把姓名板数量当作正在攻击自己的怪数。需要以真实输出、受击、死亡/历史回放分别检查覆盖情况；空日志不能证明安全。

日志解析还有一个独立限制：当前`seen`按完整文字整轮去重，同名怪重复造成同样伤害会被永久忽略。应改为带行位置/滚动证据的有限事件去重，或在当前客户端支持时用可见时间戳区分事件。添加时间戳必须同步更新解析，不能仅改界面。此项本轮未修改，不能把日志宣称为完整威胁来源。

### P1：条形CV容易读，文字只作补充

玩家和目标框保持固定位置，局部适度放大，留出连续、无遮挡的彩色条边；优先试“百分比”这一种简短状态文字，避免“数值+百分比”同时挤在细条上。当前生命已能用细条CV，法力仍较依赖OCR；重点是改善法力条可见面积，不是额外添加更多数字。

不先改变整个游戏UI缩放或分辨率，否则技能距离ROI、背包格子和所有模板都要重标。实际调整后保存新布局版本，并回放满血、半血、近零、低蓝、受击闪边、聊天/背包遮挡样本。

### P1：敌方姓名板减少重叠，辅助判断剩余敌人

如果当前菜单支持，固定敌方姓名板尺寸，试堆叠显示，减少友方姓名板干扰；目标的目标可作为“是否正在打自己”的额外线索。现代正式服的姓名板设置有官方更新说明，但当前客户端适用性需核实：[官方姓名板更新](https://worldofwarcraft.blizzard.com/en-gb/news/24244455)。

姓名板位移、遮挡和同名怪均会造成身份歧义。这只能提高识别，不直接授权在战后Tab找下一只，更不能证明画面里没有额外攻击者。

### P2：自动拾取、自我施法与交互

现有记录已能一次右键拾取，自动拾取只需核实并保持，不算新的提速成果。原生自动对自己施法若可确认，可以省去圣光术的F1选自己与Esc清目标，但必须先验证对自己生效及不影响保留敌方目标；当前不删这两步。

继续保持现有“辅助交互”关闭。官方说明其依据朝向和距离选择互动对象，而本项目已经实测会抢脚边尸体；不能把它当作硬目标F8的无条件替代。[官方交互/动作选取说明](https://worldofwarcraft.blizzard.com/en-us/news/23876525)。不引入插件或脚本输出底层状态。

## 2. 更简单的操作逻辑

建议最终收敛为：

`就绪检查 → 找目标/接近 → 输出 → 确认威胁结束 → 拾取 → 就绪检查`

恢复是就绪检查中的条件分支；没有合适目标才短巡游。全程由同一观察器监控生命、战斗标志与新受击证据。模型继续每5只看一次汇总；死亡、低血或证据异常即时触发本地保护与日志保存。

| 优先级 | 当前问题 | 简化方式 | 保留的验证 |
|---|---|---|---|
| P0 | combat、patrol、Scheduler、ensure_safe_exit都各有失败/撤退处理 | 统一威胁结算和异常处理入口；各技能返回原因，不多层重复决定撤退 | 显式停止最高优先级；成功、失败、超时均不能自动等同安全 |
| P0 | 三秒战后平静与四秒总等待并存 | 单一结算状态分别管理“连续平静时间”和“未解决威胁的总预算” | 不能刚满足脱战条件前就四秒超时撤退；仍受威胁也不能无限等 |
| P0 | 无新受击日志可能仅因筛选/去重漏掉 | 日志有记录可阻止安全结算，没有记录不清除战斗/掉血威胁 | 当前主血量、战斗标志与采集新鲜度保护保留 |
| P1 | 失败拉怪后的背包内容没变，却又开关包 | 同一运行按实际拾取/采集/出售失效缓存，加短时有效期；少空格在每次真实拾取后复查 | 不能用“每N只”假设每只固定占格；换人物/布局或人工干预失效 |
| P1 | 拾取前等待法力，拾取本身又耗时 | 脱战且生命达到拾取门槛就可拾取，让法力同时自然恢复；新拉怪前再按统一门槛判断 | 当前聊天切页要求95%生命，不能只降低recover而忘记这个前提 |
| P1 | 恢复目标70%，Policy进入REST_MANA后要求85% | 由同一资源配置派生恢复/重新拉怪阈值，保留进入与退出等待的滞回 | 两者不是每场都会冲突；战中技能保留治疗/圣印所需资源 |
| P1 | 每只重新扫描4帧候选，再扫35个固定点 | 保存击杀前最后可信目标位置，先检查近处少量候选，失败才扩展搜索 | 相机/人物移动后使旧位置失效；点击仍需新鲜拾取光标确认 |
| P2 | 每次识别重做模板颜色掩膜，四帧候选重复读/缩放尸体模板 | 固定模板预处理一次并复用 | 相同输入结果必须与旧实现一致；不调低识别阈值 |

不优先改：继续放大鼠标单步、缩短安全三秒观察、把拾取文字两帧确认减成一帧、为节约动作跳过死亡审查。原来力量祝福倒计时检查只有毫秒以下开销，不是需要删除的瓶颈；圣印保持按时间刷新。

## 本轮落地与待实施边界

本轮试做了固定鼠标掩膜和尸体模板尺度缓存。18张旧帧/空白帧、两套配置共108项输出完全一致，但交替顺序4次CPU测量的中位数未改善：默认配置7.777→8.323秒，圣骑士13.447→13.487秒。因此已撤回缓存改动，当前操作/识别代码不变；不为理论优化增加维护负担。

旧版和试验版分别保存在 `runs/ui-workflow-second-audit/interaction_vision.before.py`、`interaction_vision.candidate.py`；`replay.py`可离线对比这两个冻结版本，结果是`replay-result.json`。这个小样本CPU比较不证明在所有场景必然更慢，也不代表游戏整轮吞吐量；结论仅为没有足够收益证据。

界面布局和主流程重构尚未实施，现有坐标/配置保留。推荐实施顺序：双窗口和日志筛选 → 两块ROI标定/解析 → 统一威胁结算 → 背包失效缓存/恢复合并 → 尸体搜索优化。每项先回放，后在用户重新授权操作时小范围验证，最后才进行连续5只对比。

下一轮验证至少同时记录：成功击杀数、剩余威胁漏检/误退、每只完整周期、拾取耗时中位数和最大值、鼠标移动次数、开包次数、OCR调用数、帧龄和未知状态比例。不能仅以“杀得快了”通过验收。

现有回归复跑：374项通过（runs/ui-workflow-second-audit/tests.txt）。这些测试不覆盖本次所有新发现的边界，不能作为新界面或重构方案已验证的证据。
